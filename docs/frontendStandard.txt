FRONT-END DEVELOPMENT STANDARDS
======================================

This document is mandatory for all front-end works at Abakas.
All interns and team members must follow these rules exactly.

==================================================
SECTION 1: CORE PRINCIPLES
==================================================

1. Consistency over creativity
2. Readability over cleverness
3. Reusability over duplication
4. Maintainability over speed

If two approaches work, choose the one that is:
- Easier to read
- Easier to reuse
- Easier to maintain

STRUCTURE ENFORCEMENT RULES
--------------------------

- The app follows a DOMAIN-BASED architecture
- Domains isolate features and business logic
- Pages represent routes and must not be reused
- Components are reusable UI blocks
- API calls live ONLY inside domain /api folders
- Shared components must NOT import domain code
- Domains MAY import shared components
- Layouts are shared by default
- Domain-specific layouts may live inside the domain
- Global state belongs in /context only
- Hooks must start with `use` (lowercase)
- Folder names must be lowercase (Except for folders containing a main component)
- No circular dependencies between domains

SECTION 4: COMPONENT STANDARDS
==================================================

1. Functional components only
- All components must be written as functional components.
- Class components are not allowed, unless explicitly approved.
- Use React Hooks (useState, useEffect, etc.) instead of lifecycle methods.

Example:

// Functional component
const UserCard = ({ user }) => {
  return <p>{user.name}</p>;
};

// Class component (not allowed)
class UserCard extends React.Component {
  render() {
    return <p>{this.props.user.name}</p>;
  }
}

2. One component per file
- Each file should export only one component.
- File name must exactly match the component name (PascalCase).

Example:
src/components/UserCard/UserCard.jsx  --> exports UserCard

3. Components must be reusable
- Components should be modular and independent:
  - Accept props to handle variations
  - Should not depend on domain-specific logic
- Reusable components live in: shared/components/

Example:
const Button = ({ text, onClick, type = "button" }) => {
  return <button type={type} onClick={onClick}>{text}</button>;
}

4. No business logic inside JSX
- JSX must be purely declarative.
- All logic should be calculated before the return statement, outside JSX.

Bad example:
{users.map(u => u.age > 18 ? <p>{u.name}</p> : null)}

Good example:
const adults = users.filter(isAdult);
return (
  <>
    {adults.map(u => <p key={u.id}>{u.name}</p>)}
  </>
);

5. Key rules for all components

Rule                          | Why it matters
------------------------------|----------------
Functional components only    | Simpler syntax, easier to use hooks
One component per file        | Clear imports, easier refactor
File name = Component name    | Consistency, easier to locate
Components reusable           | Avoid duplication, enforce modularity
No business logic in JSX      | Separation of concerns, improves readability

Summary:
- Always calculate values, arrays, or conditions outside the JSX.
- Props are the only input to a component — no hardcoding domain logic.
- Follow PascalCase naming for both file and component.
- This ensures code consistency, reusability, and team efficiency.

SECTION 6: API & DATA HANDLING
==================================================

STRICT RULE:
- API calls ONLY inside /api

Components must NEVER:
- Call fetch or axios
- Handle API URLs
- Contain API logic

All API functions must:
- Be camelCase
- Use async/await
- Include try/catch
- Handle errors
- Return clean data

example:

// Get Profile function
 getProfile = async () => {
  try {
    const response = await axiosInstance.get("/agent-profile");
    return response.data;
  } catch (error) {
    throw new Error(error.response?.data?.message || "Profile fetch error");
  }
};

Export rules:
- If a file contains multiple API functions, use named exports.
- If a file contains a single API function, use a default export.

SECTION 7: STYLING RULES
==================================================

1. Bootstrap first
- Use Bootstrap classes and utilities wherever possible.
- Avoid writing custom CSS for layout, spacing, grids, or responsiveness unless necessary.
Example:
<div className="d-flex justify-content-center align-items-center p-3">
  <p>Centered text</p>
</div>

2. Custom CSS only when needed
- Write custom CSS only for unique styles that Bootstrap cannot handle.
- Custom CSS must be:
  1. Modular – specific to the component it styles.
  2. Scoped – live inside the component’s folder.
Example folder structure:
components/
└── Button/
    ├── Button.jsx
    └── Button.module.css

3. No inline styles (unless necessary)
- Avoid using inline style={{ ... }} in JSX.
- Exception: rare one-off styles approved by senior developers.

4. No !important
- Using !important overrides CSS hierarchy and breaks maintainability.
- Use proper class specificity, Bootstrap utilities, or scoped CSS modules instead.

5. Use consistent spacing
- Stick to Bootstrap spacing system (m-, p-, etc.).
- Avoid arbitrary pixel values in CSS unless component-specific design requires it.
Example:
<div className="mt-3 mb-2">Content</div>

6. Class names: kebab-case
- Use lowercase + hyphens for class names: user-card, submit-button.
- Avoid camelCase or underscores in CSS class names.

7. No unused CSS
- Remove any CSS rules that are not applied anywhere to reduce file size and confusion.

8. Group related styles
- Keep related styles together inside the CSS module.
- Example: all button styles, hover effects, and focus states in the same file.

9. Responsiveness
- Responsiveness should be handled primarily by Bootstrap (col, row, d-, flex- classes).
- Only use custom media queries if Bootstrap does not cover the requirement.
- Always test components on mobile, tablet, and desktop before submission.

Summary Rules for Interns:
- Bootstrap is the default for layout and spacing.
- Write modular CSS in component-specific folders (Button.module.css).
- No inline styles or !important unless approved.
- Use consistent spacing and kebab-case class names.
- Remove unused CSS.
- Keep related styles grouped.
- Responsiveness via Bootstrap first; media queries only if necessary.

SECTION 9: ACCESSIBILITY
==================================================

Mandatory Requirements:
-----------------------

1. alt attributes on images
   - Every <img> tag must have a descriptive alt attribute.
   - Example: <img src="logo.png" alt="Company Logo" />
   - Do not leave alt empty unless the image is purely decorative.

2. label elements for inputs
   - All form inputs must have associated <label> elements for screen readers.
   - Example:
     <label htmlFor="email">Email</label>
     <input type="email" id="email" name="email" />

3. button tags for actions
   - All clickable actions must use <button> elements rather than <div> or <span>.
   - Example:
     <button type="submit">Save</button>
   - This ensures proper keyboard navigation and accessibility support.

SECTION 11: GIT & COLLABORATION STANDARDS
================================================

Branches:
---------

Feature Branches
----------------
Format:
  feature/<short-description>

Examples:
  feature/worker-registration
  feature/visa-tracking
  feature/auth-refresh-token

Rules:
  - Always kebab-case
  - No vague names like feature/update
  - One feature per branch


Fix Branches
-------------
Format:
  fix/<what-is-broken>


Examples:
  fix/login-validation
  fix/worker-status-permission
  fix/jwt-expiry

Rules:
  - Do NOT mix new features with fixes
  - Fix branches should be small and focused


COMMIT message standards
------------------------
Format:
  <verb> <what changed> [in <scope>]

Examples:
  add worker status update endpoint
  fix token validation logic
  prevent duplicate worker status updates
  refactor auth service for clarity

Rules:
  - Start with a verb
  - Use present tense
  - Be specific

Commit Message Examples:
- "Add login form validation"
- "Refactor user card component"

SECTION X: REACT KEYS (LIST RENDERING)
==================================================

Rules:

1. Always provide a unique `key` prop when rendering lists.
   - Example (Good):
     const users = [{id: 1, name: "Alice"}, {id: 2, name: "Bob"}];
     return (
       <ul>
         {users.map(user => (
           <li key={user.id}>{user.name}</li>
         ))}
       </ul>
     );

2. Never use array index as the key unless the list is static and will never change.
   - Example (Avoid if items can be reordered or deleted):
     {items.map((item, index) => (
       <div key={index}>{item.name}</div>
     ))}

3. Keys must be:
   - Unique within the list
   - Consistent across renders
   - Preferably a unique ID from your data

4. Why keys are important:
   - Help React identify which items have changed, added, or removed.
   - Improve performance by minimizing unnecessary DOM updates.
   - Prevent bugs like component state being lost on re-render.


==================================================
SECTION X: FORM VALIDATION STANDARDS
==================================================

Rules:

1. Backend Validation is Mandatory
   - All form data must be validated on the backend using Joi.
   - Backend validation is the source of truth and cannot be bypassed.

2. Frontend Validation is Recommended
   - Use frontend validation to provide instant feedback to users.
   - Frontend validation should mirror backend rules (required fields, lengths, formats).
   - It does not replace backend validation.

3. Implementing Frontend Validation
   - Show inline error messages near input fields.
   - Validate only necessary fields to avoid over-validation.

4. Handling Backend Errors
   - Always handle backend validation errors gracefully in the UI.
   - Display errors clearly, even if frontend validation passed.
