Abakas Overseas Employment Agency Management System (AOEMS)


API Documentation - Stage 2: Core Business APIs (Workers, CVs, Partners)


Abakas – Crafting Digital Success

Introduction
This document defines all API endpoints for Stage 2 of AOEMS — the Core Business APIs focusing on worker lifecycle management, CV automation, partner access, and worker self-service. It models workers as users whose profiles evolve through many stages from account creation to deployment and integrates secure access, compliance checks, and status workflows to automate agency operations and reduce manual follow-ups.
General Information

--------------------------------------------------
Base URL: /api/
--------------------------------------------------
•	Authentication: JWT Bearer Token in Authorization header required for all endpoints.
•	Content-Type: JSON for requests/responses unless stated (file uploads use multipart/form-data).
•	Timestamps: ISO 8601 format (YYYY-MM-DDTHH:mm:ssZ).
•	IDs: BIGINT UNSIGNED.
•	Enums: Case-sensitive strings.
•	Pagination: Use page (default 1) and limit (default 10, max 100) query params.
•	Filtering: Available via query parameters per endpoint.

--------------------------------------------------
ERROR RESPONSES (ALL ENDPOINTS)
--------------------------------------------------
- 401 Unauthorized        Missing or invalid authentication token
- 403 Forbidden           Insufficient permissions
- 404 Not Found           Resource not found
- 422 Unprocessable Entity validation errors (e.g., missing fields, invalid enum)
- 500 Internal Server Error Unexpected system failure

  "error": {

  }

Role & Access
Role: Admin
Access Level: Full CRUD on all worker data and workflows

Role: Employee
Access Level: Full CRUD on assigned worker data and workflows

Role: Partner
Access Level: Read-only access to assigned workers and CVs, including CV download

Role: Worker
Access Level: Self-service access; can view own profile, status, and notifications

Role: Employer
Access Level: Limited access related to contracts only


WORKER LIFECYCLE OVERVIEW
========================

Workers undergo a structured lifecycle composed of multiple stages. Each stage is
represented in system APIs and enforced through defined business rules.

1. ACCOUNT & ACCESS EVENTS
-------------------------
- Worker account creation as a system user with role: worker
- Active, inactive, and soft-deleted account states
- Role-based access control and custom permission overrides

2. IDENTITY & PROFILE EVOLUTION
-------------------------------
- Incremental updates to personal information:
  birth details, religion, marital status, address, education,
  and physical attributes
- Photo management (3x4 photo, full standing photo)
- Regional assignment
- Status progression tracking:
  registered -> ready -> deployed

3. SKILLS, LANGUAGES, AND JOB READINESS
--------------------------------------
- Multiple job positions with experience history
- Primary job position designation
- Skill assignment and classification
- Language records with proficiency levels
- Allowed destination country configuration

4. DOCUMENT & COMPLIANCE MILESTONES
----------------------------------
- Passport issuance, expiry tracking, and document scans
- Certificate of Competency (COC) management
- Medical status tracking:
  pending, fit, unfit
- Medical report uploads
- Compliance enforcement preventing progression until medically fit

5. VISA & GOVERNMENT APPROVAL FLOW
---------------------------------
- LMIS reference number assignment
- QR code generation and linking
- Visa issuance and expiry tracking
- Automated status flow:
  waiting -> approved -> travel-ready

6. EMPLOYER & CONTRACT OUTCOMES
-------------------------------
- Employer linkage
- Contract lifecycle management:
  creation, approval, rejection, termination
- Salary and contract duration records
- Signed contract document uploads

7. TRAVEL & DEPLOYMENT
---------------------
- Travel ticket issuance
- Departure scheduling
- Travel-related document uploads
- Final deployment confirmation

8. FINANCIAL EVENTS (STAGE 3 INTEGRATION)
----------------------------------------
- Worker income tracking
- Agency expense records
- Commission calculations
- VAT and financial compliance tracking

9. NOTIFICATIONS & COMMUNICATION
--------------------------------
- Notifications for visa updates, status changes, and contract decisions
- Read and unread state tracking
- File attachments
- Push notification delivery

1. WORKER REGISTRATION & ACCOUNT MANAGEMENT
===========================================

IMPORTANT NOTES
---------------
- A "worker" is a record in `users` whose role_id references roles.name = 'worker'
- User core fields are stored in `users`
- Worker personal data is stored in `workers_personal_information`
- Worker status is stored as `status_id` referencing `worker_statuses.id`
- Every status change MUST create a record in `worker_status_history`
- Soft delete is handled via `users.deleted_at`


========================================
WORKER MODULE: CREATE & UPDATE WORKER
========================================


====================
CREATE WORKER
====================

Endpoint
--------
POST /workers

Roles Allowed
-------------
- admin
- employee

Content-Type
------------
multipart/form-data

Description
-----------
Creates a new worker user, initializes personal information,
uploads worker photos, and inserts the initial worker status history.


Database Tables Affected
------------------------
- users
- workers_personal_information
- worker_status_history


Form-Data Fields (TEXT)
----------------------

User Fields
-----------
- full_name (string, required)
- phone_number (string, required)
- email (string, optional)
- is_active (boolean, optional, default=true)

Personal Information Fields
---------------------------
- region_id (bigint, optional)
- status_id (smallint, optional)
- date_of_birth (date, YYYY-MM-DD, optional)
- place_of_birth (string, optional)
- religion (string, optional)
- marital_status (enum: Single | Married | Divorced | Widowed, optional)
- sex (enum: male | female, required)
- nationality (string, optional, default=Ethiopian)
- address (text, optional)
- education (string, optional)
- number_of_children (integer, optional, default=0)
- height_cm (decimal, optional)
- weight_kg (decimal, optional)


Form-Data Fields (FILES)
-----------------------
- photo_3x4_url (file, optional, image only)
- photo_standing_url (file, optional, image only)


Notes
-----
- role is automatically set to "worker"
- status_id inserts a record into worker_status_history
- photos are optional but validated if provided


Success Response
----------------
HTTP 201 Created

{
  success: true,
  message: "Worker created successfully",
  data: {
    id,
    role,
    full_name,
    phone_number,
    email,
    status,
    is_active,
    created_at
  }
}



====================
UPDATE WORKER
====================

Endpoint
--------
PATCH /workers/{id}

Roles Allowed
-------------
- admin
- employee

Content-Type
------------
multipart/form-data

Description
-----------
Updates user-level fields, personal information, worker photos,
and worker status if status_id changes.


Database Tables Affected
------------------------
- users
- workers_personal_information
- worker_status_history (only if status_id changes)


Form-Data Fields (ALL OPTIONAL)
------------------------------

User Fields
-----------
- full_name
- phone_number
- email
- is_active

Personal Information Fields
---------------------------
- region_id
- status_id
- date_of_birth
- place_of_birth
- religion
- marital_status
- sex
- nationality
- address
- education
- number_of_children
- height_cm
- weight_kg


Form-Data Fields (FILES)
-----------------------
- photo_3x4_url (file, optional, replaces existing)
- photo_standing_url (file, optional, replaces existing)


Photo Update Rules
------------------
- If a new photo is uploaded:
  - The old Cloudinary file is deleted
  - DB URL and public_id are updated
- If no file is sent:
  - Existing photo remains unchanged


Status Update Rule
------------------
- If status_id is different from the current value:
  - Insert a new record into worker_status_history
  - Update workers_personal_information.status_id


Success Response
----------------
HTTP 200 OK

{
  success: true,
  message: "Worker updated successfully",
  data: {
    id,
    full_name,
    phone_number,
    status,
    updated_at
  }
}

DELETE / ARCHIVE WORKER
--------------------------------------------------
Endpoint:
DELETE /workers/{id}

Roles Allowed:
- admin
- employee

Description:
Soft delete sets users.deleted_at.
Hard delete removes the user and cascades
to all related worker records.

Query Parameter:
- hard=true | false

Example:
DELETE /workers/128?hard=true

Soft Delete Response:
{
  "success": true,
  "message": "Worker archived successfully",
  "data": {
    "id": 128,
    "deleted_at": "2026-02-01T12:00:00Z"
  }
}

Hard Delete Response:
{
  "success": true,
  "message": "Worker deleted permanently",
  "data": {
    "id": 128
  }
}

========================================
WORKER SUB-MODULE: PASSPORT MODULE
========================================

NOTES
-----
- worker_id refers to users.id
- Passport data is stored in workers_passport_information
- Each worker can have ONLY ONE passport record
- passport_number is UNIQUE and NOT NULL at DB level
- Passport files are stored externally (Cloudinary); DB stores URL, public_id, and resource type

Base Path:
/workers/{worker_id}/passport


--------------------------------------------------
CREATE PASSPORT
--------------------------------------------------
Endpoint:
POST /workers/{worker_id}/passport

Roles Allowed:
- admin
- employee

Description:
Creates passport information for a worker.
Fails if a passport record already exists.

DATABASE TABLE AFFECTED:
- workers_passport_information

Request:
- Content-Type: multipart/form-data
- URL parameter:
  - worker_id (path) - Worker ID

- Form data fields:
  - passport_number (string, required): Passport number (5-50 chars)
  - passport_issue_date (string, required): ISO 8601 date (YYYY-MM-DD)
  - passport_expiry_date (string, required): ISO 8601 date (must be after issue date)
  - passport_issuing_country (string, optional): Default is "Ethiopia"
  - passport_scan (file, required): Passport scan file (image or PDF)

Response:
201 Created

{
  "success": true,
  "message": "Passport created successfully",
  "data": {
    "id": 22,

    "passport_number": "A123456",

    "passport_expiry_date": "2030-01-01T00:00:00.000Z",
    "passport_issuing_country": "Ethiopia",
    "passport_scan_url": "https://res.cloudinary.com/your_cloud_name/raw/upload/v1234567890/passports/worker_128",
    "passport_scan_public_id": "passports/worker_128",
    "passport_scan_resource_type": "raw",
    "created_at": "2026-02-01T11:10:00.000Z",

==================================================
ERROR HANDLING SUMMARY
==================================================
- 401 Unauthorized — invalid or missing JWT token
- 403 Forbidden — insufficient permissions
- 404 Not Found — resource does not exist
- 422 Unprocessable Entity — invalid or missing input data
- 500 Internal Server Error — unexpected server failure


==================================================
PAGINATION & FILTERING SUMMARY
==================================================
- Use query parameters `page` and `limit` for pagination on list endpoints.
- Support filtering on relevant fields like status, region, name, etc.
- Responses include pagination metadata (total counts, pages, current page).


==================================================
JOI VALIDATION SCHEMA NOTES (FOR DEVELOPERS)
==================================================
- All request bodies are validated using Joi schemas.
- Examples:
  - Worker creation: required strings for full_name, regex validation for phone_number, date validation for date_of_birth with age checks.
  - Status updates: enum checks and cross-field validation.
- Validation errors return 422 with detailed messages per field.
